## 0. Background — why this step

P7 migrated schema's *property dispatch* to grammar2 + Walker, but
the *comment-lookup surface* (modelOverrideName, strfmtName,
typeName, enumName, defaultName, nameOverride, allOfName,
allOfMember, aliasParam, ignored) was ported as a private helper
layer (`comment_lookups.go`) that re-runs `Lex(Preprocess(cg))` on
every call. ~12 calls per typed declaration today; far more once
items/parameters/responses migrate. Symptoms:

- Schema-private helpers re-implement what is logically a generic
  "find swagger:X arg in CommentGroup" — duplication waiting to
  happen across builders.
- Each call re-lexes the same comment group.
- The schema builder's two entry points (`Build` → `inferNames` →
  `applyBlockToDecl`, and `BuildFromType` → recursive
  `buildFromType`) both call `ScanCtx.FindComments` to materialize
  comment groups for type declarations, then run the regex-shaped
  lookups. These are in tension with the Walker pattern that
  already runs successfully at the property layer.

The earlier draft of this work tried to "lift the regex utilities
into grammar2 primitives" — same shape, lower layer. Fred pushed
back: that's still bridge-style thinking. The bolder move is to
push **discovery** itself through the Walker, eliminating the
ad-hoc lookups entirely.

## 1. Design intent

> The Walker is the right pattern. We aren't using it for naming /
> classification because the original v1 codebase didn't use
> Tagger (its regex-based ancestor) in those places — but the
> Walker can subsume them.

Concretely:

- **One parse per declaration.** Each `*ast.CommentGroup` becomes a
  `grammar2.Block` exactly once per build pass. No more
  `Lex(Preprocess(cg))` re-runs per question.
- **Walkers do the asking.** Every "look at this comment to find X"
  is a Walker (or Walker callback) invocation against a
  pre-parsed Block. Each context (top-level decl, named-basic,
  named-struct, struct-field, alias, classifier-only) gets a
  purpose-built Walker.
- **Discovery flows with traversal.** Names, strfmt overrides,
  type overrides, enum overrides, etc. are detected as the
  recursive `buildFromType` descent encounters comments —
  not by repeated post-hoc questioning.

This is a structural change, not a rename. It collapses
`comment_lookups.go` and most of `inferNames` / the FindComments
calls inside `buildFromType`'s recursive descent.

## 4. Block-passing topology — parse once, walk many

Today, `s.decl.Comments` is the top-level comment group; nested
type discovery calls `ctx.FindComments` for each sub-type. Each
call group is independently parsed.

**fred** yes I agree that we need a cache here. Recursive descent is not done concurrently, so no issues with that.

### 4.1 The cache

Add a small cache on the Builder:

```go
type Builder struct {
    // ... existing fields ...
    blockCache map[*ast.CommentGroup]grammar2.Block
}

func (s *Builder) parseBlock(cg *ast.CommentGroup) grammar2.Block {
    if cg == nil { return nil }
    if b, ok := s.blockCache[cg]; ok { return b }
    if s.blockCache == nil { s.blockCache = map[*ast.CommentGroup]grammar2.Block{} }
    b := grammar2.NewParser(s.ctx.FileSet()).Parse(cg)
    s.blockCache[cg] = b
    return b
}
```

Keyed on the `*ast.CommentGroup` pointer — deterministic and
stable across one Build pass. The cache is per-Builder, scoped to
one type declaration's build; cross-declaration sharing is not
needed (and would risk lifetime issues).

### 4.2 The new lookup contract

Every site that today does either:

```go
cmt, _ := s.ctx.FindComments(pkg, name)
if val, ok := s.strfmtName(cmt); ok { ... }
```

or:

```go
if val, ok := s.strfmtName(afld.Doc); ok { ... }
```

becomes:

```go
block := s.parseBlock(commentGroup)
walker := /* configure callbacks for this site */
block.Walk(walker)
```

The walker callbacks write directly to whatever `tgt` /
`schema` / `s.Name` / etc. the caller would have written to after
the lookup returned. Discovery flows with traversal.

### 4.3 Annotation kinds → Walker callbacks

Most annotation lookups today have ShapeNone or take an
IDENT_NAME / TYPE_REF arg. Today these flow through the lexer's
TokenAnnotation slot, which we already index via
`block.AnnotationKind()`. For sub-typed args we need either:

1. A lightweight `block.AnnotationArg() (string, bool)` accessor
   for IDENT_NAME-style annotations on classifier blocks
   (StrfmtBlock has `Name`, TypeBlock has `Name`, etc.). **Most
   blocks already expose this** — only `swagger:name` (AnnName)
   currently lands as UnboundBlock and loses the IDENT_NAME, per
   the existing `feedback_grammar2_dispatch_subtleties.md`. Fix:
   give `swagger:name` its own typed block (e.g. `*NameBlock`
   with `IDENTName string` field) — already logged as P9 cleanup.

2. A new Walker callback shape (e.g. `OnAnnotation(kind, arg
   string)`) — heavier and feels like the wrong layer.

Path (1) is cleaner. Each classifier-shaped block exposes its
typed argument; the Walker reads it directly via type-assertion at
the dispatch site (the dispatch logic knows what to expect for
each annotation kind).

**fred** yes let's try (1)

### 4.4 What about FindComments itself?

`ScanCtx.FindComments` is a scanner-level utility for looking up
comment groups attached to a type by package + name. The schema
builder uses it because, during recursive type descent, it needs
the doc comment of a Go type that isn't the originally declared
one (e.g. an alias's RHS).

**P9 already plans to drop `ScanCtx.FindComments`** — once schema
no longer needs it, no other builder uses it. After this plan
lands, the FindComments calls should naturally disappear:

- Alias and named-type cases: the TYPE_REF resolution already
  yields the `*scanner.EntityDecl` for the resolved type — that
  decl carries `.Comments`. No FindComments needed.
- Interface case: same — `s.ctx.FindModel(pkg, name)` returns
  `*EntityDecl` with comments attached.

So the FindComments rip-out is an emergent benefit of this redesign.

**fred** yes indeed

## 6. Risk register

### 6.1 v1's "find any line" vs grammar2's "first annotation"

v1's regex utilities scan every line. grammar2's `Parse` returns
the FIRST annotation in source order. Cases where a comment has
TWO `swagger:model` lines (or any double-classifier shape) would
behave differently.

Fred's call from the prior session:
> If there is a `swagger:model useThisName` buried somewhere to be
> caught by the regexp specifically, I'd believe this a typical
> regexp quirk that we should not reconduct.

So we accept the divergence. Mitigation: golden run pre-merge to
catch any fixture relying on the regex quirk.

**fred** yes. Our integration test harness is rather reliable and improving every day. So let's see how it goes.

### 6.2 Multi-annotation comments (intentional)

A doc comment can legitimately carry multiple annotations:
```go
// swagger:model
// swagger:strfmt date-time
type T time.Time
```

The Walker handles this naturally — both ModelBlock and
StrfmtBlock annotations land in the same Block? Actually NO —
`Parse` returns one Block keyed on the first annotation. Multi-
annotation comments need either:

(a) `Parse` to return a slice of Blocks (one per annotation), or
(b) per-line scan via the lexer-tokens approach (what the current
    `comment_lookups.go` does).

This is a real grammar2 design question. Current v1 fixtures
DO have multi-annotation comments (checked: classification
fixture has `// swagger:model` + `// swagger:strfmt` patterns).

**Proposed resolution:** add `grammar2.ParseAll(cg) []Block` that
returns one Block per annotation, plus an `Unbound` shell for
shared prose. Schema builds a single Walker pass over the
slice. This is a new grammar2 feature; would land in Phase A as
A4. Adds ~80 LOC to grammar2.

**fred** yes this is the right call. We'll see in the final cleanup (P9) which of all these methods
should survive if some prove to be unused.

### 6.3 Cache lifetime + concurrency

The block cache is per-Builder. Builders are constructed per
top-level decl; not shared across goroutines. Cache map is fine
without synchronisation.

**fred** correct

### 6.4 Test coverage

Each phase ends with a green run of the full suite + lint.
Goldens MUST NOT be updated silently — any drift requires a
write-up in the PR description (e.g. the multi-annotation
divergence in §6.1).
