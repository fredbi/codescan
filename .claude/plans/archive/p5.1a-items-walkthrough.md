## 1. v1 call chain — traced

The smallest useful example: `SetMaximum` on an `items` target.

```
codescan.Run(opts)
  → spec.Builder.Build()
    → buildModels() / buildDiscoveredSchema() / ...
      → schema.Builder.buildFromType(tpe, tgt)                 (schema.go:277)
        → schema.Builder.createParser(name, schema, ps, fld)   (schema.go:1378)
            taggers := schemaTaggers(schema, ps, nm)           (schema/taggers.go)
            if field is array → parseArrayTypes(taggers, elt, ps.Items, 0)
                → itemsTaggers(items, 0)                       (items/taggers.go:20)
                    returns e.g. []parsers.TagParser{
                      parsers.NewSingleLineTagParser("items0Maximum",
                        parsers.NewSetMaximum(Validations{items})),
                      ...
                    }
            return parsers.NewSectionedParser(opts...)
        → sp.Parse(fld.Doc)                                    (schema.go:134/723/951/1207)
            → sectioned_parser.go:parseLine for each line
                → rxMaximum.MatchString(line)                  (validations.go:46)
                    → sm.builder.SetMaximum(val, excl)         (items/validations.go:15)
                        → spec.Items.Maximum = &val            (spec library)
```

**Four `sp.Parse(field.Doc)` call sites** in `schema.go` —
lines 134, 723, 951, 1207. Each is a natural routing point for
the feature flag (§3).

**Key contract:** the bridge-tagger writes through
`ifaces.ValidationBuilder` **unchanged**. Both v1 and v2 call
`items.Validations.SetMaximum(val, excl)`. The interface is the
parity-preserving seam — we only replace the *caller*, not the
callee.

## 2. v2 bridge-tagger — sketch

Single entry point, conceptually a free function; call it from
the routing point as a replacement for `sp.Parse(fld.Doc)`.

```go
// internal/builders/items/bridge.go (new file)

package items

import (
    "github.com/go-openapi/codescan/internal/ifaces"
    "github.com/go-openapi/codescan/internal/parsers/grammar"
)

// ApplyBlock writes every items-level validation property found
// in b at the given depth to target. level is 1-indexed (level 1
// matches `items.maximum: 5`, level 2 `items.items.maximum: 5`).
func ApplyBlock(b grammar.Block, target ifaces.ValidationBuilder, level int) {
    for p := range b.Properties() {
        if p.ItemsDepth != level {
            continue
        }
        dispatchItemsKeyword(p, target)
    }
}

func dispatchItemsKeyword(p grammar.Property, t ifaces.ValidationBuilder) {
    switch p.Keyword.Name {
    case "maximum":
        if p.Typed.Type == grammar.ValueNumber {
            t.SetMaximum(p.Typed.Number, p.Typed.Op == "<")
        }
    case "minimum":
        if p.Typed.Type == grammar.ValueNumber {
            t.SetMinimum(p.Typed.Number, p.Typed.Op == ">")
        }
    case "multipleOf":
        if p.Typed.Type == grammar.ValueNumber {
            t.SetMultipleOf(p.Typed.Number)
        }
    case "minLength":
        if p.Typed.Type == grammar.ValueInteger {
            t.SetMinLength(p.Typed.Integer)
        }
    case "maxLength":
        if p.Typed.Type == grammar.ValueInteger {
            t.SetMaxLength(p.Typed.Integer)
        }
    case "pattern":
        t.SetPattern(p.Value)
    case "minItems":
        if p.Typed.Type == grammar.ValueInteger {
            t.SetMinItems(p.Typed.Integer)
        }
    case "maxItems":
        if p.Typed.Type == grammar.ValueInteger {
            t.SetMaxItems(p.Typed.Integer)
        }
    case "unique":
        if p.Typed.Type == grammar.ValueBoolean {
            t.SetUnique(p.Typed.Boolean)
        }
    case "collectionFormat":
        if ov, ok := t.(ifaces.OperationValidationBuilder); ok {
            if p.Typed.Type == grammar.ValueStringEnum {
                ov.SetCollectionFormat(p.Typed.String)
            }
        }
    case "enum":
        // Delegate to v1's ParseEnum via the existing SetEnum for
        // now. Step 8 later swaps in internal/parsers/enum/.
        t.SetEnum(p.Value)
    case "default":
        t.SetDefault(p.Value)
    case "example":
        t.SetExample(p.Value)
    }
}
```

**Notes on the sketch:**

- No regex. The lexer already tokenized; `ItemsDepth` is already
  on the Property from P1.2.
- Typed values come pre-converted from P1.5 (`Typed.Number`,
  `Typed.Integer`, `Typed.Boolean`). The `Typed.Type` check
  guards against conversion failures (those produced a
  diagnostic upstream; the bridge-tagger silently drops the
  value, same as v1's pattern of early-return on regex mismatch).
- `collectionFormat` is an `OperationValidationBuilder` concern —
  items doesn't implement it, but the v1 tagger table includes
  it for symmetry. The type-assertion gate replicates that.
- **enum stays delegated to v1** for step 6. Step 8 swaps to the
  new sub-parser.

## 3. Routing point — feature flag

The flag gates **which code runs** at each `sp.Parse(fld.Doc)`
site. Two candidates:

**Option A — wrap at the call site.** At each of the four
`sp.Parse(fld.Doc)` sites in schema.go:

```go
if s.ctx.Options().UseGrammarParser {
    applyBlockHere(fld.Doc, schema, ps, …)
} else {
    if err := sp.Parse(fld.Doc); err != nil { ... }
}
```

**Option B — make SectionedParser.Parse itself branch.** When the
flag is set, internally it delegates to `grammar.Parser.Parse` +
the bridge-tagger dispatch, writing through the same
ValidationBuilder it was going to write to anyway.

Option B keeps the call-site code identical and localizes the
routing to one place, but it requires `SectionedParser` to carry
the flag and the bridge-tagger surface. Architecturally worse
(legacy type now knows about grammar).

**Decision: Option A.** The call sites already have access to
`s.ctx` (Builder context holds Options). One helper function,
four call-site wrappers.

```go
// schema.go
func (s *Builder) parseDoc(sp *parsers.SectionedParser, doc *ast.CommentGroup, ...) error {
    if s.ctx.Options().UseGrammarParser {
        return s.applyBlockToSchema(doc, ...)
    }
    return sp.Parse(doc)
}
```

## 4. Parity vs divergence — the design tension

**The problem:** `TestParity` asserts v1 output == v2 output. W2
§2.6 mandates v2 should diverge from v1 on three enum quirks.
These two requirements directly conflict during migration.

Options:

**(A) Parity-first, then divergence.** Step 6–10 migrate every
builder preserving v1 behavior EXACTLY (including quirks).
`TestParity` stays green end-to-end. After all builders migrate
and legacy code is gone (post-step-10), a separate
"quirk-fix" commit phase:
- Swaps `SetEnum(p.Value)` → `enum.Parse(p.Value)` + `WithEnum(values...)`.
- Updates the golden fixtures for affected cases (enum-overrides
  case B/D/E).
- Removes `TestParity` at P6.4 alongside the flag.

**(B) Divergence-first, allowlisted parity.** `TestParity` grows
a per-fixture "intentional divergence" allowlist. Each quirk-fix
commit adds an allowlist entry and updates the golden. More
machinery; more room for silent regressions.

**(C) Skip TestParity on divergent fixtures.** Coarse version of
B — if a migration commit knowingly breaks parity on fixture X,
drop X from parityFixtures. Loses safety net.

**Recommendation: (A).** Quirk fixes are tiny, localized, and
the post-migration state is the natural moment to take them.
Keeps the migration itself maximally conservative.

**Implication for the enum sub-parser:** `internal/parsers/enum/`
is in the repo (step 5 landed) but sits **unused** during steps
6–10. The bridge-taggers call `SetEnum(p.Value)` which routes
through v1's ParseEnum. Parity is held. After step 10, a
"quirk-fix" commit swaps the bridge-tagger to call `enum.Parse`
and updates the golden for `enhancements_enum_overrides.json`.

This matches the yaml sub-parser's current status — landed, no
consumer yet, consumer arrives at P5.4 (operations builder).

## 6. Risks surfaced by this walkthrough

1. **Parity is NOT automatically maintained** — step 8 naively
   would break it. The §4 "parity-first" sequencing avoids this
   at the cost of landing the sub-parser as dead code for the
   duration of P5. Accepted trade-off.

2. **Typed.Op carries the `<` / `>` exclusivity bit.** The v1
   `SetMaximum` signature is `SetMaximum(val, exclusive bool)`
   — `exclusive == true` means strict (the `<` variant). My
   dispatcher has `p.Typed.Op == "<"`; double-check in the
   actual bridge-tagger code that `<=` doesn't erroneously land
   in this branch (it shouldn't — `Op` is populated by a string
   match, not substring). Added a test case to exercise the
   distinction.

3. **Items-level `collectionFormat` via type assertion.** v1's
   items `Validations` doesn't implement `SetCollectionFormat`
   (per survey), but v1 includes the tagger in the items table
   anyway. The assertion-guarded path matches that — a
   `collectionFormat:` at an `items.` depth on a non-operation
   target silently drops. Parity preserved.

4. **Struct field with `parseArrayTypes` at depth >= 1.** The v1
   `parseArrayTypes` recursion generates itemsTaggers per level
   via `itemsTaggers(items, level)`. The v2 equivalent needs
   equivalent per-depth awareness. `ApplyBlock(b, target, level)`
   handles one level; the schema-side caller (P5.1b) recurses
   into `items.Items` and calls `ApplyBlock` again with
   `level+1`.
