# P5.1b (revised) — schema builder migration walkthrough

Date: 2026-04-22
Status: ✅ landed as commit `1701ae7`. The redesign in this doc
(grammar owns description classification, bite-the-bullet at one
commit per builder) became the template for P5.2 → P5.5 + P6.1.
Supersedes: shadow-path commit `6f62186` (subsumed).
Companion: `p5.1a-items-walkthrough.md`, `p5-builder-migrations.md`

## 0. Why this document exists

The first attempt at P5.1b (commit `6f62186`) hit an unexpected
design wall. The chunking plan in `p5-builder-migrations.md`
assumed a clean "parser vs builder" seam: the grammar parser
produces typed `Block` values, bridge-taggers dispatch them to the
existing `ValidationBuilder` interface, legacy regex taggers keep
running unchanged until the flag flips everywhere at P6.

That seam held for items (P5.1a) because items' only job is
writing validation targets — no title, no description, no
line-claiming role. Schema-level parsing revealed the seam is
wrong: the legacy regex taggers play a **dual role**:

1. **Claim** matched lines from the `SectionedParser`'s line-by-
   line walk, so they don't fall through to the description
   accumulator.
2. **Write** the parsed value to the target schema.

Under the flag, when we skipped (1) we produced parity breaks
like:

```
- description: "The photo urls for the pet.\nThis only accepts jpeg or png images."
+ description: "The photo urls for the pet.\nThis only accepts jpeg or png images.\n\nitems pattern: \\.(jpe?g|png)$"
```

The `items pattern:` body leaked into the description because no
tagger claimed it and the SectionedParser's description accumulator
is indiscriminate (any line that matches nothing falls through).

The shadow-path workaround — keep v1 taggers registered, let the
grammar bridge overwrite the same values — defers the real
migration indefinitely. Every subsequent builder (parameters,
responses, operations) has the same dual-role problem.

## 1. Fred's rationale — redesign now, not later

> "We are trying to minimize risk by chunking changes, but at this
> point, we've just realized that our pre-established divide for
> chunking (taggers vs builders) is not fully applicable. In reality,
> pushing there to maintain strict isolation (based on theoretical
> ground only) will raise the risk by deferring the discovery of
> wrong micro-designs to the last minute."

Chunking exists to catch design errors early. If a chunk's
boundary hides the error, the chunking is wrong. The correct move
is to **redraw the boundary now**, before compounding the error
across parameters/responses/operations/routes.

The correct boundary: the **grammar parser owns line
classification**. Description, title, and property bodies all come
from the parser's typed `Block`. Bridge-taggers dispatch Properties
to ValidationBuilder-family targets. Legacy regex taggers go away
entirely on the flag-on path — not deferred to P6, but starting at
P5.1b.

## 2. The grammar is already 90% ready

`internal/parsers/grammar/parser.go` already partitions tokens
during preprocessing:

- `parseTitleDesc` (lines 430–464) iterates **pre-annotation**
  tokens and accumulates **only `TokenText`** into paragraphs.
  Keyword / block-head / YAML / raw tokens are silently ignored
  from prose:
  ```go
  case TokenEOF, TokenAnnotation,
       TokenKeywordValue, TokenKeywordBlockHead,
       TokenYAMLFence, TokenRawLine:
      // Ignored in the title/description slice.
  ```
- `parseBody` (lines 477–513) iterates post-annotation tokens and
  accumulates keyword tokens into `Property` entries; prose
  (`TokenText`, `TokenBlank`, `TokenRawLine` outside a fence) is
  **dropped**.

So `block.Title()` and `block.Description()` are *already* clean of
keyword noise. The schema builder just needs to consume them
instead of the `SectionedParser`'s line-based description callback.

## 3. What `schema.ApplyBlock` owns

A new `internal/builders/schema/bridge.go` helper — the schema-
side sibling of `items.ApplyBlock`. It takes a `grammar.Block` and
a cluster of write targets, dispatches:

| Grammar `Property.Keyword.Name` | Legacy tagger                          | Target method                   | Notes                               |
|---------------------------------|----------------------------------------|---------------------------------|-------------------------------------|
| `maximum`                       | `NewSetMaximum(schemaValidations{ps})` | `SetMaximum(val, excl)`         | `Typed.Op == "<"` → exclusive       |
| `minimum`                       | `NewSetMinimum(...)`                   | `SetMinimum(val, excl)`         | `Typed.Op == ">"` → exclusive       |
| `multipleOf`                    | `NewSetMultipleOf(...)`                | `SetMultipleOf(val)`            |                                     |
| `minLength` / `maxLength`       | `NewSetMinLength(...)` / `NewSetMaxLength(...)` | `SetMinLength(v)` / `SetMaxLength(v)` |                          |
| `pattern`                       | `NewSetPattern(...)`                   | `SetPattern(v)`                 |                                     |
| `minItems` / `maxItems`         | ditto                                  | `SetMinItems(v)` / `SetMaxItems(v)` |                                     |
| `unique`                        | `NewSetUnique(...)`                    | `SetUnique(v)`                  |                                     |
| `enum`                          | `NewSetEnum(...)` → `ParseEnum(...)`   | `SetEnum(raw)` (still v1 route) | Stays on v1 ParseEnum for step      |
| `default`                       | `NewSetDefault(scheme, ...)`           | `SetDefault(v)`                 | v1 parses per scheme.Type           |
| `example`                       | `NewSetExample(scheme, ...)`           | `SetExample(v)`                 | ditto                               |
| `required`                      | `NewSetRequiredSchema(schema, nm)`     | writes to PARENT schema `Required[]` | boolean value, enclosing-schema seam |
| `readOnly`                      | `NewSetReadOnlySchema(ps)`             | writes `ps.ReadOnly`            |                                     |
| `discriminator`                 | `NewSetDiscriminator(schema, nm)`      | writes `schema.Discriminator = nm` | enclosing-schema seam                |
| `in`                            | `NewMatchIn()` (match-only)            | — (no write)                    | Grammar already excludes from prose; no dispatch needed |
| `deprecated`                    | — (not in schemaTaggers today)         | `ps.Deprecated = v`             | Currently unreachable via schemaTaggers; grammar exposes it — leave as-is unless a fixture needs it |

**Multi-line:**

| Grammar `Keyword.Name`          | Legacy tagger                          | Target                          | Notes                               |
|---------------------------------|----------------------------------------|---------------------------------|-------------------------------------|
| `extensions` / `infoExtensions` (YAMLExtensionsBlock) | `NewYAMLParser(WithExtensionMatcher(), WithSetter(schemaVendorExtensibleSetter(ps)))` | `ps.Extensions` via JSON unmarshal | Grammar already extracts each `x-*: v` line into `base.extensions`; schema bridge iterates and calls `ps.AddExtension` |

**Not in the schema-level dispatch** — items-level (`ItemsDepth ≥ 1`)
dispatches stay in `items.ApplyBlock` as per P5.1a.

**Known v1 quirks surfaced:**

- `NewSingleLineTagParser("type", NewSetDefault(scheme, ...))` in
  `schemaTaggers` — the tag name "type" but the parser writes
  `Default`. `NewSetDefault`'s internal regex matches `default:`,
  not `type:`, so the "type" registration is effectively dead (the
  SectionedParser dispatches by the tag's own regex, not by the
  name). Grammar path: ignore. Document as a deferred quirk.

## 4. The three field call sites

All three (processAnonInterfaceMethod:730, processInterfaceMethod:
958, processStructField:1214) follow the same shape, paraphrased:

```go
sp := s.createParser(name, enclosing, &ps, afld)
if err := sp.Parse(afld.Doc); err != nil { return err }
```

**Under the flag** they become:

```go
if s.ctx.UseGrammarParser() {
    s.applyBlockToField(afld, enclosing, &ps, name)
} else {
    sp := s.createParser(name, enclosing, &ps, afld)
    if err := sp.Parse(afld.Doc); err != nil { return err }
}
```

Where `applyBlockToField`:

1. Parses `afld.Doc` via `grammar.NewParser(s.decl.Pkg.Fset).Parse(...)`.
2. Guards: if ps.Ref is already set and !DescWithRef, only dispatch
   `required` (mirrors legacy `refSchemaTaggers`).
3. Otherwise: sets `ps.Description` from `block.Description()`, with
   the existing enum-desc suffix logic applied (moved from the
   SectionedParser callback into a helper).
4. Calls `schema.ApplyBlock(block, schemaTargets{...}, 0)` for
   level-0 properties.
5. Calls `items.ApplyBlock(block, schemaValidations{target}, level)`
   for each items level collected by `collectItemsLevels(...)`.

The top-level model declaration call site (buildFromDecl:134) gets
the same treatment but also handles `WithSetTitle`: it sets
`schema.Title = block.Title()`.

## 5. Title handling

`SectionedParser` has a `setTitle` callback; only the top-level
call uses it. The field-level calls have **no title** — v1
treats the first prose paragraph of a struct field doc as
description, not title. The grammar's `base.title` is the first
paragraph; for field-level calls we must concatenate it back into
the description output so parity holds:

```go
desc := block.Description()
if title := block.Title(); title != "" {
    if desc == "" {
        desc = title
    } else {
        desc = title + "\n\n" + desc
    }
}
ps.Description = desc
```

Easy parity-preserver. For the top-level call, title stays
separate. This is the one shape adjustment where the grammar's
title/description split doesn't map 1:1 to the legacy field-level
notion.

## 6. The `enum` delegation question

The enum sub-parser landed at step 5 (`internal/parsers/enum/`)
but has no production consumer yet per W2's parity-first
sequencing. The schema bridge in P5.1b revised keeps
`SetEnum(p.Value)` — routing through the v1 ParseEnum path — for
parity. Step 8 (post-migration quirk-fix) swaps it to
`enum.Parse(p.Value)` + `target.WithEnum(values...)` + golden
update, same plan as before.

## 8. Risks surfaced

1. **`default:` and `example:` need scheme-aware parsing.** v1's
   `NewSetDefault` / `NewSetExample` take a `*oaispec.SimpleSchema`
   with Format/Type to decide how to parse the raw value (e.g.,
   `default: 3` with `Type: "integer"` becomes `int64(3)`, with
   `Type: "string"` becomes `"3"`). The grammar's Typed field is
   not schema-aware — it classifies by keyword-declared
   ValueType, not by target schema type. Resolution: the bridge
   builds a `SimpleSchema` from `ps.Type/Format` at dispatch time
   and delegates to the existing `parsers.ParseValueFromSchema`
   helper (extracted from validations.go). Same code path as v1;
   only the caller changes.

2. **`required:` writes to the ENCLOSING schema's `Required[]`,
   not `ps` itself.** The bridge-tagger signature for
   schema-level needs to carry both `ps` and the enclosing
   `schema`. Same two-target structure the legacy taggers
   already use via `NewSetRequiredSchema(schema, nm)`.

3. **`$ref`-mode field doc uses a shorter tagger list
   (refSchemaTaggers).** The flag-on path mirrors by only
   dispatching `required` when `ps.Ref != "" && !DescWithRef`.

4. **Description post-processing (enum-desc suffix).** The legacy
   callback appends `schema.Extensions[x-go-enum-desc]` onto the
   description when present. Must be applied after grammar's
   description retrieval. Already have the helper
   `parsers.GetEnumDesc`. One-line inline.

5. **TOP-level call site uses `schema=schema` (self-referencing
   enclosing).** The `required` dispatch there writes to the
   same schema it's parsing — v1 does this implicitly via the
   tagger's signature. Mirror exactly.

6. **Parity test is the canary.** Every fixture in `parityFixtures`
   must stay green. Per-fixture diffs during development point
   to missing or mis-mapped keywords.

## 10. Out-of-scope, flagged

- **Diagnostics surfacing.** Grammar emits diagnostics
  (context-invalid keyword, invalid number, etc.). Legacy path
  silently drops. P5.1b revised stays silent (discards
  diagnostics) to preserve parity. Integration of diagnostics
  into the scanner's warning pipeline is a separate P7 task
  (already captured in forthcoming-features.md §?).

- **Container-type re-detection.** The grammar doesn't
  re-classify field types; `ps.Type`/`ps.Format` come from
  `buildFromType` before dispatch. Resolution: bridge reads
  `ps.Type[0]` and `ps.Format`, same as v1 — it's already
  written at dispatch time.
